# Local plugins

Pico loads `.mjs` Runtime entries from this directory when the Runtime starts. Each entry exports a default plugin object with `id`, `name`, `version`, and a Runtime `activate(context)` contribution. Executor-only manifests may omit the Runtime contribution. Runtime modules are loaded independently from Pico's compiled server.

A plugin package can contain several contributions together. ChatGPT, Model Parameters, Auto Thread Title, and Vision are shipped as independent packages and are loaded from their `.mjs` entries; each can be disabled or reloaded through Plugin settings. Run `npm run plugins:build` to build Runtime entries and the ChatGPT and Model Parameters browser bundles in sequence. `npm run plugins:build:chatgpt` is retained as an alias for the full first-party package build. Pico's normal server and main Web UI bundles do not compile plugin business implementations. Tests that need optional first-party plugins inject their fixtures explicitly.

## Tool visibility

Tools are enabled per Thread for model projection. This controls whether a tool is offered to the model; the Permissions plugin still makes invocation-level authorization decisions. Framework Executor tools are enabled by default. Runtime plugin tools default to disabled unless their plugin opts in with `defaultToolsEnabled: true`; that default is applied when a new root Thread is created. Other Executor tools default to disabled and can be enabled per Thread through the plugin service or Tools panel. Existing Threads keep their saved settings.

Workflow plugins can read the current Thread's tool state with `threads.tools(threadId)`, which returns each tool's `source` and `enabled` value, and change it with `threads.setToolEnabled(threadId, toolName, enabled)`. Child Threads inherit their parent's settings. `threads.create(..., { parentThreadId, toolOverrides })` can apply sparse per-tool overrides to the child. The collaboration plugin exposes the same option as `tool_settings` on `spawn_thread`.

MCP servers have a `visibleByDefault` setting, which defaults to `false`. Pico captures it when a root Thread is created, even if that server has not started yet. A Thread's explicit per-tool setting takes precedence, and later server setting changes affect newly created Threads only. Child Threads inherit the parent's captured defaults and explicit settings.

## Auxiliary model calls

A Runtime plugin that calls `context.models.complete` must declare `modelCalls: true` on its exported plugin object. Undeclared plugins are rejected by Runtime, and Plugin settings only show model selection for declared plugins. Declared plugins inherit the current Thread's model unless the user selects a fixed model for that plugin. Runtime-owned context compaction uses a separate internal call path.

The Runtime serves a plugin's registered UI entry from its own package directory. The entry runs in a sandboxed iframe as a logic controller. It sends a bounded, serializable component tree over the transferred `MessagePort`; the Pico Web UI validates the tree for the active slot and renders all visible controls itself. The iframe's pixels are hidden. There is no HTML, Markdown, URL, image, CSS, class, raw dimension, DOM, or React-tree channel. Invalid or unrecognized descriptions fail closed with a host-owned unavailable message. Plugin UI assets are public static files; credentials and mutable plugin state remain behind authenticated Runtime APIs.

## Theme contributions

Runtime plugins may register host-applied appearance data from `activate` with `context.ui.registerTheme({ id, label, appearance, variables, background?, brandIcon?, pairedThemeId?, brandLabel? })`. `appearance` is `light` or `dark`; theme IDs are plugin-local and returned records use `pluginId` plus a namespaced `pluginId:id`. `variables` must be a plain object of at most 256 entries, using names matching `--pico-[a-z0-9-]+`. This validates the public token namespace, not whether every token currently has a host consumer. The host applies only recognized, registered roles.

Variable values are inert CSS tokens: color literals, supported color/gradient functions, simple font sizes and font-family lists are accepted; `url()`, `var()`, `expression()`, braces, semicolons, and unsupported functions are rejected. A plugin can register at most 32 themes. Optional `background` and `brandIcon` each identify a registered Web UI `entry` and a safe relative asset `path` under that package's `webui/` directory. `brandIcon` is rendered by the host in the sidebar and welcome marks while its theme is active; the host constructs its asset URL. Optional `brandLabel` is a plain printable 1–40 character string that replaces the sidebar wordmark only while that theme is active. Optional `pairedThemeId` names another theme ID local to the same plugin; when that opposite-scheme theme is available, the sidebar toggle prefers it. It cannot contain a plugin namespace or reference another plugin. The entry is served only while registered by a page, UI contribution, or theme. Theme records returned from registration and `pluginInfo()` are copies, so callers cannot mutate Host state.

List theme backgrounds and brand icons in `webui/theme-assets.json`, for example `{"assets":["assets/background.svg","assets/whale.svg"]}`. Paths are relative to `webui/` and must name existing image files. The framework constructs both URLs; plugins provide only `{ entry, path }` descriptors and cannot inject markup, CSS, or arbitrary URLs. Publishing verifies and snapshots the listed images with the UI release. `--pico-theme-background-size`, `--pico-theme-background-position`, and `--pico-theme-background-repeat` control the image placement, and `--pico-material-backdrop` can provide a glass effect such as `blur(16px)` on framework surfaces. Omitting these roles preserves the built-in appearance.

The browser stores the latest available explicit theme under separate `pico.appearance.recent.light` and `pico.appearance.recent.dark` localStorage keys; it still reads the earlier combined `pico.appearance.recent` JSON value. System-following never overwrites those choices. The theme toggle uses an available paired theme first, then the recent explicit choice for the target scheme, then the built-in theme. Preferences and recent choices synchronize across tabs. Theme registrations are owned by the plugin and are removed on disable, unload, failed activation, or reload. A reload that fails reactivating the new version restores the previously active plugin and its registrations.

Third-party package layout:

```text
plugins/
  my.plugin.mjs
  my.plugin/
    webui/
      index.html
      ...self-contained assets...
```

The Runtime entry ID and directory name must match. Register each page or UI component with an `entry` ID; the corresponding files are served from `my.plugin/webui/`. `index.html` can select the requested semantic view from `viewType` and `viewId` query parameters. The host initializes the iframe with protocol version 1 and transfers one `MessagePort`; do not use cross-frame DOM access or depend on Pico's UI framework. The stable host message shapes and TypeScript authoring types are in `src/plugins/ui-protocol.ts` for first-party development.

The host probes the optional `/pico-plugin-ui-bridge.js` before initialization. The bridge reports plugin UI script errors and acknowledges the host probe; it does not make the plugin view itself ready. After mounting its controller and sending its first description, an entry can post `{ type: "pico:plugin-ui:ready", attemptId: init.attemptId }` through the transferred port. Pico's Settings → Developer page records the iframe load, bridge response, ready response, and runtime errors. Plugins do not report dimensions or size visible host controls.

The init message is `{ type: "pico:plugin-ui:init", protocolVersion: 1, pluginId, entry, viewType, viewId, settings }`. A controller sends `{ type: "pico:plugin-ui:render", tree }`; only documented component nodes are accepted. Host interactions return as `{ type: "pico:plugin-ui:action", actionId, value? }`. UI requests use `{ type: "pico:plugin-ui:request", id, action, ... }` and receive a matching `pico:plugin-ui:response`. Supported capabilities include same-plugin API routes, non-secret model fields, the owning plugin's registered pages, selected Threads/messages, and bounded plain-text notices/errors. The host may send settings, context, events, and toolbar lifecycle updates. A plugin must independently validate each action ID and route it to its own behavior. Requests outside the bridge capabilities are ignored or rejected.

The component schema supports literal `text`, `heading`, and `paragraph`; host `group`, `card`, `actions`, and `list` containers; a bounded text `table`; host `disclosure`; `button`; single-line `textInput` (including a host-rendered password input); `checkbox`; auto-growing `textArea`; and `select` with bounded text options. Every field is validated against an exact per-node field list, per-slot node allowlist, tree depth/node count, aggregate text size, row/cell/option count, action ID format/count, and enumerated control settings. Unknown fields fail closed. Text is inserted as text. No arbitrary links, markup, images, styles, CSS classes, widths, heights, or `max-height` values are part of the schema.

Slot catalog and ownership:

| Slot                     | Allowed content                                                            | Host ownership                                                                       |
| ------------------------ | -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| `thread.toolbar`         | Text, grouped/card details, actions, buttons, text input, textarea, select | Host button, popover shell, focus, dismissal, viewport placement and outer scrolling |
| `composer.action`        | Text and button                                                            | Host placement and control sizing                                                    |
| `composer.model`         | Text, group, button, select, checkbox, single-line text input              | Host 32px control row; popover shell is host-owned                                   |
| `composer.status`        | Plain text nodes only                                                      | Host alignment, line height, truncation and tone                                     |
| `sidebar.panel`          | Text, groups/cards, actions and controls                                   | Host placement, available width and outer scrolling                                  |
| `tool.result`            | Text, paragraph, group, actions and button                                 | Host ToolCard shell and lifecycle; plugin cannot replace it                          |
| Registered Settings page | Same bounded schema as sidebar content                                     | Host Settings shell, navigation, width and scrolling                                 |
| Thread Info              | Host-owned feature, not a plugin slot                                      | Host shell and controls, including rename/archive                                    |

`composer.model` has a fixed 32px row contract. Other cards and groups size to their content within the parent width and viewport. Long text wraps. Dialogs and popovers scroll at their host-owned outer surface. A `textInput` stays one line, is constrained by its parent, and scrolls horizontally with the caret. A `textArea` wraps and grows from a semantic minimum: `compact` (2 rows), `standard` (4), or `large` (6); the renderer controls actual pixel sizes. Maximum length limits accepted content only. Goal and completion fields use `large`; constraints use `standard`.

Global Memory is a Settings page. Project Memory is a Thread toolbar popover. Thread Info remains entirely host-owned. Registered Settings pages render inside the host Settings shell. Plugins cannot provide the outer shell, arbitrary alignment, dimensions, spacing, colors, breakpoints, focus rules, scroll containers, Popover/Dialog shells, or CSS/layout escape hatches.

Plugin notices and errors are plain text, with host-owned tone, scope, duration and dismissal. They are transient UI state and are not appended to Canonical History or Session history. Framework-only Executor/Runtime banners may have host-defined actions; plugin notice payloads cannot define actions.

The example plugin contributes an agent tool, the `/notes` command, a Thread toolbar action, private persistent state, and append-only canonical records. Local plugins execute as trusted code inside the Pico Runtime. Browser UI code runs in the iframe sandbox and only receives the bridged capabilities above.

Stable contribution surfaces are `tools`, the `step` / `projection` / `model` / `toolBatch` / `toolInvocation` pipelines, `commands`, semantic `ui` slots, plugin `state`, and the append-only `canonical` logger. Pipeline registration order is deterministic by plugin load order and registration order. The ChatGPT example contributes an OpenAI-compatible provider ID, a `model` pipeline interceptor, authenticated plugin API routes, plugin-local OAuth/preferences state, a slash command, a Settings page, and a `composer.model` semantic UI contribution.

Pipeline input/output types are defined in `src/contracts/plugin-pipeline.ts` and inferred from the registered stage. A projection plugin that changes `turns` must keep its provenance mappings accurate: `canonicalStartSeq` / `canonicalEndSeq` identify an inclusive source range, and `turnStartIndex` / `turnEndIndex` identify the corresponding half-open range in the final `turns` array. An omitted source has an empty turn range; a replacement summary may own multiple turns. Keep Tool Calls and their results in the same source group. Mark added plugin context as `kind: 'plugin'`, and update all affected indexes when inserting or removing turns. Runtime compaction uses these mappings to select complete source groups without depending on plugin IDs; incomplete or overlapping mappings block automatic compaction. The mappings determine the safe boundary and request identity; the compaction helper still summarizes the selected Canonical input/output records.

Runtime plugins may register HTTP routes and Settings pages using stable IDs. The `.mjs` Runtime module cannot inject arbitrary script or markup into the host Web UI; its separately packaged UI is mounted only in the registered semantic location.

The UI slots render in distinct places: `thread.toolbar` sits in the selected Thread action row beside Tools, `composer.action` sits next to Send, and `sidebar.panel` appears in the scrollable navigation area. A component contribution in `thread.toolbar` can set `supportsPopover: true` to make its button open the component in a popover. Contributions with a `command` invoke that registered slash command from the selected Thread. A sidebar panel without a command can provide label and description only; toolbar and composer actions without a command appear disabled.

Slash command handlers receive whitespace-split `args` for simple options and `context.rawArgs` for the original text after the command name, preserving spaces and newlines for commands that accept prose. The built-in `/project-context` command uses plugin-local state keyed by Project ID and a projection interceptor to share explicitly maintained context across a Project's Threads. `/project-context set` followed by a new line and text replaces it; `/project-context clear` removes it. This context is never harvested from canonical history or shortened automatically.

The `toolBatch` stage exposes the committed calls and an `execute(call)` function. A scheduler can wrap `execute` or reorder calls while delegating each unchanged call; the default stage runs them concurrently. Preserve each call's ID, name, and arguments. Pico checks the durable Execution records after the stage and will not start the next Model Step until the whole batch is settled.

The `step` stage wraps one full agent-loop iteration: its Model Step and any Tool Batch produced by that Model Step run before the interceptor returns at the next safe boundary. A short-circuit that leaves durable work unprocessed pauses the Thread so the Runtime does not spin without progress.

Slash commands stay explicit actions and do not become user Messages. Pico records an append-only receipt before running a command handler; retrying the same request ID will not invoke the handler again. If a handler throws or its outcome is uncertain, inspect the Thread or plugin state before submitting it again with a new ID.

## Workflow ownership and configuration

The default Runtime workflows include `pico.workspace`, `pico.project-context`, `pico.commands`, `pico.collaboration`, `pico.permissions`, and `pico.auto-thread-title`. Set `PICO_DISABLED_PLUGINS` to a comma-separated list of default plugin IDs, or use `RuntimeOptions.disabledBuiltinPlugins`, to disable a default implementation before loading a replacement. Selection happens at startup; loaded plugins and pipeline registration order are inspectable through `/api/plugins`. Disabling permissions removes its rules, approval interaction, and interceptors from the active workflow. It does not change Executor isolation.

`context.threads` exposes Thread lookup, listing, bound Executor lookup, available tool discovery, creation, same-Project message delivery, and title updates. `context.threads.updateTitle(threadId, title)` records each actual change as an append-only plugin Canonical History record and emits the normal `thread.updated` event. `pico.auto-thread-title` uses the first user message and configured model to title new Threads after their first agent step. The collaboration plugin owns the agent-facing spawn/message tools and guidance. Message senders provide stable IDs so a retry does not create a second message. Child Threads retain ordinary Thread and Message semantics.

`context.executions` provides lookup, explicit failure, and subscriptions to execution changes. The `toolInvocation` input provides an abort signal, tool source, `fail(reason, result?)`, and `invoke()`. Permission policies and approval state live in `pico.permissions` plugin state. Its static API routes are `GET /api/plugins/pico.permissions/threads?threadId=...`, `PUT .../rules`, and `POST .../approvals`; its toolbar and pending decision actions come from its independently loaded Web UI package. Existing core approval tables and permission settings are migrated once to plugin state, preserving canonical audit records.

## Canonical facts and state

`canonical.list(threadId)` reads all committed fact kinds. Prefer `canonical.read(threadId, { afterSeq, limit })` for bounded forward pagination (maximum 1,000 records), and save the last processed sequence in plugin state when needed. `canonical.subscribe(threadId, listener)` delivers committed records while the Runtime is alive. It does not replay history or provide a durable queue; reconnecting consumers resume with `read`. Notifications are emitted after the outer transaction commits, rolled-back writes emit nothing, and observer errors cannot roll back committed facts. Plugin-owned subscriptions are disposed on activation failure or shutdown.

`canonical.append` remains restricted to the owning plugin namespace. Existing records cannot be edited. `state.transaction(operation)` groups state and canonical writes atomically, while `state.subscribe(listener)` observes committed changes to the owning plugin's state. State writes with identical serialized values do not emit another update.

## Executor contributions

One manifest can provide optional `activate(context)` for Runtime contributions and optional `activateExecutor(context)` for environment tools. At least one entrypoint is required. Install self-contained Executor `.mjs` bundles under `executor-plugins/` or `PICO_EXECUTOR_PLUGIN_DIR`; Runtime-only bundles are ignored by the Executor loader and Executor-only bundles are ignored by the Runtime loader. Executor activation receives `tools.register(definition, execute)`. Tool execution receives the environment's `workspacePath`, stable `executionId`, and abort `signal`.

Host and Remote Executors load their own bundles. Container Executor copies bundles to `/opt/pico/executor-plugins` and discovers the tool schemas actually registered inside the container. Bundle dependencies must be included in the self-contained file. The default `pico.executor-tools` package registers file, search, patch, and shell tools through the same registry. Failed plugin registrations do not expose a partial toolset.

Remote `/api/info` uses protocol version 1 and returns validated tool schemas; no particular tool names are mandatory. Model tool surfaces combine the bound Executor's schemas with Runtime tools. A name registered by both sources is rejected with a diagnostic instead of silently routing to one implementation. Chat Threads expose Runtime plugin tools without attaching an external Executor toolset.

## UI components and commands

Components can contribute to `thread.toolbar`, `composer.action`, `sidebar.panel`, `composer.model`, and `tool.result`. Only `thread.toolbar` components can set `supportsPopover: true`; the host renders their control in the Thread action row and opens the component in a popover when clicked. The host always owns the Tool Card shell and lifecycle. A `tool.result` component can add a small result-area action or detail; it cannot replace the card. These components may specify `toolNames`, and the host mounts them only for matching calls while the execution is pending. Their context is limited to the Thread ID and an execution ID/status pair; it does not expose the Thread record, Tool arguments, or result payload. `pico:plugin-ui:context` updates that context; `pico:plugin-ui:event` delivers events for the owning plugin. The typed client exposes `subscribeContext` and `subscribeEvents`.

All first-party plugin pages and components send `PluginUiNode[]` directly with `client.render(tree)` and route host actions through `client.subscribeActions` or the equivalent MessagePort handler. The iframe DOM and React render output are not part of the UI protocol. Every slot uses an explicit node allowlist, exact node fields, bounded text and tree sizes, and validated action IDs. Plugin text renders as plain text. Composer status accepts text only. Notice/error requests carry plain text; the host owns severity, scope, and dismissal and keeps these notices out of Canonical History and Session history.

A `command` request contains the complete slash command text. The host injects the owning plugin and current Thread, and the server verifies command ownership before executing it. The command uses a stable request ID and the ordinary command receipt path. A plugin frame cannot invoke another plugin's command, open another plugin's page, call another plugin's API, or access the host DOM.
