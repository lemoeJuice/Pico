# Context Pipeline：Thread 状态队列与结构化压缩设计 v1

状态：本文记录目标设计；本次实现的具体范围和仍未完成的目标见第 12 节。第 1–11 节中的强一致性与持久化条目是设计目标，不能一概视为当前实现已满足。

## 1. 目标与边界

为每个 Thread 建立一个有版本的当前上下文投影，并让普通历史、历史追加、投影替换/清空以及所有会读取或修改该投影的操作经过同一串行队列。每次模型请求都从队列内取得一致的投影快照，再临时生成该次请求的 system 与插件上下文。模型调用在队列外异步执行；完成后回队列校验版本，避免迟到结果覆盖期间发生的新事实或用户操作。

压缩只改变后续请求使用的投影，不改写或删除 Canonical 原始事实。投影必须可持久化、重启恢复，并能在 rewind 后按所选历史分支恢复或安全重建。失败操作不得部分改变当前状态，也不得丢弃尚未消费的工作。

本文把 Runtime 结构化 compact 与 Rolling Context 分开定义：前者把当前投影的一个安全前缀替换为摘要并保留近期原文；后者在工具阶段后检查已完成轮次，并使用插件已经拥有的胶囊替换合格前缀。两者均只编辑投影，不互相重复压缩，也不要求修改 Vision 或其它视觉插件。

## 2. 概念与不变量

- **Canonical History**：Thread 的追加式原始事实，包括普通消息、完整模型/工具调用及结果、rewind 标记和其它已提交事件。它是审计及重建依据，不因 compact 或 Rolling Context 而修改、覆盖或删除。
- **Thread Projection State**：从 Canonical 与有效投影操作构成的持久化当前上下文状态。包括投影版本、分支/rewind 锚点、按原有模型输入结构排列的历史项、结构化摘要替代项、来源引用以及待处理游标。它不是 Canonical 原始事实。
- **临时请求上下文**：一次请求专属的 system 内容及插件上下文/工具定义。每次请求重新生成并合并到请求快照，不永久拼入历史投影，也不由 compact 摘要取代。保存诊断时遵循敏感信息边界。
- **完整轮次**：一次模型响应及其产生的全部工具调用和对应结果。用户消息保持独立；不能把未完成调用或缺少结果的调用链当作可压缩边界。
- **结构保真**：保留消息角色、内容块顺序和类型、调用 ID/name/arguments 与 result 配对、多模态引用以及必要的来源边界。不得先把历史摊平为文本再尝试猜回结构。

关键不变量是：Canonical 原文永远可追溯；有效投影始终对应一个确定 Thread 分支及 Canonical 水位；所有投影读写和普通历史操作在同一 Thread 队列中线性化；异步模型结果必须通过提交前版本检查；失败不产生部分投影变更。

## 3. Thread 串行状态队列

每个 Thread 有一个逻辑串行队列。以下操作全部进入该队列：普通历史查询/读取、history append、追加到已完成对话、投影替换、投影清空/reset、compact、Rolling Context 检查及提交、rewind/切换分支、持久化恢复或修复，以及任何影响这些操作所见状态的状态读取或修改。不能只把写操作排队而允许读操作看到半提交状态。

队列提供串行事务语义：一个任务读取某一完整版本，计算候选状态，在一次提交边界持久化并发布新版本；失败时旧版本仍是唯一可见状态。读取也排队并返回不可变快照，调用方不能持有可变内部引用。队列可按 Thread 独立并行，不要求全 Runtime 单线程。

长时间模型调用不得占住队列。请求准备阶段在队列内生成一致输入快照并记录其 `threadId`、分支身份、projection version、Canonical watermark、操作 ID 和源 hash，然后释放队列调用模型。模型返回后，再把候选提交排回同一队列；如影响其正确性的任一身份或版本已变化，则拒绝提交并保留原投影及待处理工作。重试必须重新读取和重新生成候选，不可沿用过期快照盲目写入。

在队列调用期间发生的普通历史追加不能被延迟模型结果覆盖。实现可选择：若追加属于候选之外且不改变候选前缀来源，则按明确的可重基规则把候选应用到当前版本；否则令操作冲突并重新计算。v1 建议采用严格版本相等提交，冲突时保持候选为待处理工作并重新排队，简化证明和恢复。

队列任务需要可持久恢复的操作身份/阶段，至少能区分待执行、模型调用中、候选待校验、已提交、冲突需重算和失败。进程在调用中崩溃时，重启不得猜测模型是否完成；可以安全重试纯辅助摘要请求，但需使用幂等键或把其视为新尝试，期间投影维持旧版本。队列本身是调度机制，正确性不能依赖内存队列在进程重启后仍存在。

## 4. 每次请求的上下文构造

在主模型请求开始前，Runtime 在 Thread 队列中读取当前持久投影及其版本，然后执行该请求需要的 Projection 阶段，并临时生成 system 和插件上下文、工具列表及其它本次请求注入项。最终冻结为请求快照，所有 Provider retry/transport attempt 对应的输入身份须按实际转换规则记录；重试若改变模型或格式，应有各自明确的实际输入快照。

临时 system/插件上下文不回写 Thread Projection State。下一次请求重新计算它们，以反映最新插件状态、权限和设置。若某插件提供的是历史摘要胶囊或投影历史替代，则该数据由插件按其持久语义维护，并通过 Projection 阶段加入；不能把每次临时注入误认为历史，也不能因重新生成 system 就重复累积到历史中。

Runtime compact 的输入范围是请求历史投影的原有结构。对 compact helper 的单次辅助请求，需定义一个仅针对 compact 操作的临时提示，追加在该历史结构末尾，以要求对所给历史进行压缩并保留约束。compact 辅助请求使用与对应主请求相同的 cache key/缓存分区身份，避免因为使用另一把 key 而人为失去可复用缓存；实际 Provider 是否按 key 分区、是否保留缓存、TTL 和命中情况不作保证，必须观察并标成未知或实测值。该辅助请求不应把主请求的 system/插件状态永久并入投影，也不执行工具。

## 5. Runtime 结构化 compact

### 5.1 输入、边界与输出

compact 基于队列内取得的当前投影快照操作。候选前缀必须保持其原有结构和顺序，按完整轮次边界选择；保持最近策略规定的完整模型/工具调用轮次原文。compact 提示作为额外的末尾项附加给辅助摘要请求，不重排、不扁平化、不修改源快照。

多模态内容必须按类型处理。近期轮次中出现的图片/图像引用保持原样并继续进入主投影；不得让文本摘要替代最近轮次的图片。更早被摘要覆盖的区域可由摘要描述已知观察，但不得伪造图片内容或引用失效的媒体对象。v1 不要求 Vision 插件改变任何行为、契约或状态；它仍按已有路径处理本次主请求中的视觉输入。

辅助响应必须符合无工具摘要契约：非空、限长、无 tool call，并能映射到候选来源。提交的投影由摘要替代项加上最近保留的完整结构原文组成；它不删除历史事实，也不得留下悬空调用或孤立结果。摘要项需有稳定 ID、源区间/record IDs、源 hash、版本、创建尝试及模型调用元数据；普通历史项保持原有结构。

### 5.2 原子提交与失败

模型返回后，Runtime 回到 Thread 队列，核对分支、版本、水位、候选边界与来源 hash。校验成功才以单一原子提交持久化新投影版本；旧版本可留作恢复/审计依据。若校验失败、调用错误/超时/取消、响应无效、摘要超限、写入失败或进程恢复发现结果不确定，则当前投影不变。未消费候选与工作游标保留，可供明确重试或在新版本上重新计算。

提交后的重启恢复应从持久化投影变更记录/快照与 Canonical History 验证源关系，重建同一结果。若校验发现投影无法证明来自当前分支，则不能把旧分支摘要用于新分支；应回退到最近有效投影或从所选 Canonical 分支重建原文投影，再重新评估压缩。投影清空/reset 也必须是队列内的版本化操作，不能抹除 Canonical。

## 6. Rolling Context 工具后检查

Rolling Context 在工具阶段完成及其结果落入 Canonical 后，按 Thread 队列检查投影状态。只有完整轮次已闭合、所有工具调用与结果齐全且无活动执行冲突时，才推进插件自己的消费游标并选择候选范围。决策基于实际完整轮次，不得因某一个并行工具先完成就提前压缩。

压缩/替换时使用 Rolling Context 插件已经生成并持久拥有的胶囊；本路径不再为相同来源调用另一份摘要，也不重写胶囊内容。插件依据来源 IDs/hash、胶囊版本和当前分支确认匹配后，以胶囊替换 eligible prefix，保留策略规定的最近完整轮次原文以及所有更新的未消费工作。摘要前缀、完整工具链与尾部新消息保持 Canonical 顺序和来源映射。

若胶囊不存在、来源不匹配、轮次未完成、模型仍运行、投影版本发生竞态或持久化失败，保持旧投影和旧消费游标；后续安全边界可重试。成功时应在同一原子事务中提交新投影及已消费水位，确保崩溃后不是“游标前进但原文仍被当作已处理”，也不是重复消费造成丢失。

## 7. 持久化、重启与 rewind

Projection State 需要有明确 schema/version、thread ID、branch/rewind anchor、Canonical watermark、projection version、结构化项及来源身份。持久化形式可采用版本化事件加可重建快照；最终选型由实现阶段审查现有 Store 确定。本设计不把 Plugin State 当作 Canonical History，也不把摘要写回去覆盖消息事实。摘要和替换项是派生投影数据，必须可校验、可失效、可重建。

每次 rewind 均由 Canonical rewind/branch 语义确定目标路径。投影状态若完整来源集合属于新选分支且 watermark 不越过目标边界，可复用；否则失效并从该分支 Canonical 原文重建，再重新应用来源完全匹配的有效 compact/胶囊操作。不得把已被 rewind 丢弃的分支内容留在当前 Projection 中。rewind 与任何正在进行的异步摘要通过同一队列和版本检查竞争：先提交 rewind 则旧请求不能写回；先提交摘要则 rewind 随后按新锚点重建/选择投影。

重启恢复、schema 迁移和损坏修复都必须在 Thread 队列保护下完成。对于不能可靠映射的旧摘要或记录，保守回退为原文可重建投影，保留原始 Canonical 与审计资料，不猜测边界。

## 8. Token、缓存与可观测性边界

结构化投影可精确说明哪些内容和源记录进入 Model Input，但 token 数只有在对应模型/Provider tokenizer 可用时才能精确计算。字符数、其它 tokenizer 或前一次调用的 token usage 只能作为估算/历史观察，不能冒充本次输入精确长度。请求完成后报告 Provider 实际返回的 usage 字段，并将缺失字段标为 unavailable。

相同 cache key 是请求身份上的设计约束，不是缓存命中的证明。前缀缓存行为、缓存 TTL、缓存读写费用、key 的实际 Provider 语义，以及工具/system 对前缀的影响，均以服务商文档和运行中可观察的字段为准；若 API 不返回则记为 unknown。摘要产生的成本与未来复用收益分开报告，不宣称未经测量的净节省。实际 Model Input 视图可显示结构、来源、摘要替代与估算；不得显示或持久化访问 token、Authorization header、连接密钥、秘密配置或插件私有凭据。

## 9. 敏感信息与错误处理

摘要模型接收当前结构化投影和末尾的压缩提示。工具结果、用户消息、图片描述、代码和 JSON 一律视作不可信数据，不得把其中的指令提升为 system 指令；保留工具定义以维持请求前缀，但摘要调用不得执行工具，出现工具调用时拒绝摘要。敏感字段应遵循现有 Provider 错误脱敏和日志边界，不因需要 provenance 而保存原始凭据或完整认证头。摘要/诊断记录只留来源引用、hash、固定错误类别及非敏感状态。

发生错误时，公开给 Thread/用户的错误信息需采用安全类别和可行动描述；不把 Provider 原始异常正文、请求头或插件任意对象原样写进 Projection、Canonical、通知或摘要审计。失败尝试可以记录无敏感信息的状态，但不得使投影半更新。

## 10. 实施分期与验收

建议按队列和版本化快照、结构化 compact、Rolling Context 胶囊消费的顺序实施，并与既有 `/compact` 和 Canonical compaction fact 统一。下列条目是目标验收范围，实际完成情况见第 12 节。

验收至少覆盖：

1. 并发 history read/append、compact、投影替换/清空、rewind 均按每 Thread 队列得到一致顺序；读者从不见半提交版本。
2. 模型等待期间发生 append、reset 或 rewind 时，迟到结果不能覆盖新版本；冲突时旧投影不变且待处理工作仍可重试。
3. 每次主请求临时生成 system/插件上下文；其更新不污染持久历史。compact helper 保持历史原结构，提示只追加在末尾，并沿用主请求 cache key 身份。
4. compact 保留完整工具调用/结果配对及最近轮次图片；其它视觉插件无需改动。非文本内容、坏响应、取消、超限和存储故障均原子失败。
5. Rolling Context 仅在工具阶段后、轮次完整时判定；复用已有插件胶囊替换前缀，来源或版本不匹配时不前进消费游标、不丢未消费工作。
6. 重启后恢复相同投影；rewind 后没有错误分支信息，旧分支摘要不能泄漏到新分支。损坏/不兼容状态可回退到 Canonical 原文重建。
7. 实际 token usage、cache key、缓存命中/TTL/计价只报告可观察数据；未知值明确标记。凭据哨兵不进入摘要、持久化状态、错误或诊断。

## 12. 本次实现与尚未实现的边界

- `ThreadContextState` 是 Runtime 内存中的每 Thread 投影状态，提供排队的读取、追加、替换、清空和版本检查；每次当前模型投影经过 Rolling Context 后与状态同步。它是可从 Canonical 及插件事实重建的进程内状态，不是独立持久化的投影表。历史预览不会倒退当前状态。
- Runtime compact 使用完整的最终结构化投影，末尾追加压缩提示，保留工具定义但不执行摘要返回的工具调用；其 Responses cache key 与主请求相同。摘要完成后在队列中复核版本、Canonical 水位、完整活动分支与模型选择，再记录 compact fact 和更新状态。fact 同时绑定摘要实际看到的整个活动分支，防止 rewind 后把较晚轮次的信息带回较早分支。旧格式 fact 保持原有兼容行为。
- 最近完整模型调用与工具结果按既有保留规则保留。视觉插件仍按原路径为每次请求注入图像；图像能否再次出现依赖插件原有的匹配、预算及素材可用性，不能承诺所有图片永久保留。
- Rolling Context 仍通过已有 projection 中间件在下一次模型步骤检查完整轮次，消费其持久化的胶囊，并同步生成的普通投影；本次补充中断后 pending 胶囊的恢复和可重试失败状态。Rolling 插件状态和 Canonical 写入不全部经过该内存队列。
- 因此，第 3、6、7 节所述将所有 Canonical 历史操作、Rolling 状态变更与独立投影持久化纳入同一持久事务的更强目标尚未完整实现；当前使用已有持久事实恢复投影，并在 compact 提交时做冲突检查。不能据此宣称所有跨进程或跨插件操作均已线性化。
